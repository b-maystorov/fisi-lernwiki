# 2.6 Bedarfs und Anforderungsanalyse durchführen

In diesem Kapitel geht es darum, den Bedarf eines Kunden oder einer Fachabteilung systematisch zu erfassen und daraus konkrete Anforderungen abzuleiten.

Eine Bedarfs und Anforderungsanalyse ist die Grundlage für eine passende IT-Lösung. Ohne eine saubere Analyse besteht die Gefahr, dass Hardware, Software oder Dienstleistungen falsch geplant werden.

Für Fachinformatiker für Systemintegration ist dieses Thema wichtig, weil technische Entscheidungen immer aus echten Anforderungen entstehen sollten und nicht nur aus Vermutungen.

---

## Kurz erklärt

Eine Bedarfsanalyse klärt, welches Problem oder welcher Bedarf vorhanden ist.

Eine Anforderungsanalyse beschreibt danach genauer, welche Eigenschaften die Lösung haben muss.

Einfach gesagt:

| Analyse             | Frage                                 |
| ------------------- | ------------------------------------- |
| Bedarfsanalyse      | Was wird gebraucht und warum?         |
| Anforderungsanalyse | Was muss die Lösung konkret erfüllen? |

Der Bedarf beschreibt also eher das Problem oder Ziel.  
Die Anforderungen beschreiben die konkreten Bedingungen an die Lösung.

---

## Unterschied zwischen Bedarf und Anforderung

Bedarf und Anforderung werden oft verwechselt, bedeuten aber nicht genau das Gleiche.

| Begriff     | Bedeutung                               | Beispiel                                                              |
| ----------- | --------------------------------------- | --------------------------------------------------------------------- |
| Bedarf      | ein allgemeiner Bedarf oder ein Problem | Mitarbeiter können nicht effizient im Homeoffice arbeiten             |
| Anforderung | konkrete Bedingung an die Lösung        | Laptop mit VPN-Zugang, Webcam, Headset und Festplattenverschlüsselung |

Der Bedarf ist meistens der Ausgangspunkt.  
Die Anforderungen entstehen durch Analyse, Rückfragen und technische Bewertung.

Ein Kunde sagt zum Beispiel:

> Wir brauchen bessere Computer.

Das ist noch keine konkrete Anforderung.

Durch Rückfragen kann daraus werden:

> Die neuen Arbeitsplätze sollen mehrere Office-Programme, Browser, Videokonferenzen und die interne Fachsoftware gleichzeitig flüssig ausführen können.

Daraus können technische Anforderungen entstehen:

- mindestens 16 GB RAM
- SSD mit mindestens 512 GB
- Dockingstation-Unterstützung
- zwei externe Monitore
- Windows 11 Pro
- TPM für Verschlüsselung
- WLAN und LAN
- zentrale Verwaltung möglich

---

## Ziel der Bedarfs- und Anforderungsanalyse

Das Ziel ist, eine Lösung zu planen, die zum tatsächlichen Einsatz passt.

Dabei sollen folgende Fragen beantwortet werden:

- Welches Problem soll gelöst werden?
- Wer nutzt die Lösung?
- Welche Aufgaben sollen unterstützt werden?
- Welche Systeme sind bereits vorhanden?
- Welche technischen Voraussetzungen gibt es?
- Welche Sicherheitsanforderungen gelten?
- Welche rechtlichen Vorgaben müssen beachtet werden?
- Welche Kosten sind akzeptabel?
- Welche Lösung ist langfristig sinnvoll?
- Wie wird geprüft, ob die Lösung erfolgreich ist?

Eine gute Analyse reduziert spätere Fehler, Missverständnisse und unnötige Kosten.

---

## Ist-Zustand und Soll-Zustand

Ein wichtiger Teil der Analyse ist der Vergleich zwischen Ist-Zustand und Soll-Zustand.

### Ist-Zustand

Der Ist-Zustand beschreibt die aktuelle Situation.

Dabei wird geprüft:

- Welche Hardware wird aktuell genutzt?
- Welche Software ist installiert?
- Wie ist das Netzwerk aufgebaut?
- Welche Probleme treten auf?
- Welche Prozesse gibt es?
- Welche Benutzer sind betroffen?
- Welche Sicherheitsmaßnahmen sind vorhanden?
- Welche Dokumentation existiert bereits?

### Soll-Zustand

Der Soll-Zustand beschreibt, wie die Situation nach der Umsetzung aussehen soll.

Dabei wird festgelegt:

- Welche Funktionen sollen vorhanden sein?
- Welche Leistung wird benötigt?
- Welche Sicherheitsmaßnahmen sollen umgesetzt werden?
- Welche Systeme sollen integriert werden?
- Welche Benutzer sollen Zugriff erhalten?
- Welche Dokumentation soll erstellt werden?
- Welche Kriterien müssen bei der Abnahme erfüllt sein?

Der Vergleich zwischen Ist und Soll zeigt, welche Maßnahmen notwendig sind.

---

## Beteiligte Personen

Bei einer Anforderungsanalyse gibt es oft mehrere Beteiligte.

| Beteiligte Person                   | Rolle                                   |
| ----------------------------------- | --------------------------------------- |
| Kunde / Auftraggeber                | beschreibt Ziel, Budget und Erwartungen |
| Endbenutzer                         | arbeitet später mit der Lösung          |
| IT-Abteilung                        | prüft technische Machbarkeit            |
| Datenschutzbeauftragter             | bewertet Datenschutzthemen              |
| Informationssicherheitsbeauftragter | bewertet Sicherheitsanforderungen       |
| Einkauf                             | kümmert sich um Beschaffung             |
| Geschäftsleitung                    | entscheidet bei größeren Investitionen  |
| Support / Betrieb                   | betreut die Lösung später               |

Nicht alle Beteiligten haben die gleiche Sichtweise.

Ein Endbenutzer achtet oft auf Bedienbarkeit.  
Die IT achtet auf Wartbarkeit und Sicherheit.  
Die Geschäftsleitung achtet auf Kosten und Nutzen.

Eine gute Analyse berücksichtigt diese Perspektiven.

---

## Methoden der Anforderungsaufnahme

Anforderungen können auf verschiedene Arten gesammelt werden.

| Methode                | Beschreibung                                                   |
| ---------------------- | -------------------------------------------------------------- |
| Interview              | gezielte Fragen an Kunden oder Benutzer                        |
| Fragebogen             | strukturierte Sammlung vieler Informationen                    |
| Beobachtung            | Arbeitsabläufe direkt anschauen                                |
| Workshop               | Anforderungen gemeinsam mit mehreren Beteiligten erarbeiten    |
| Dokumentenanalyse      | vorhandene Dokumentationen, Verträge oder Prozesse prüfen      |
| Systemanalyse          | bestehende Hardware, Software und Netzwerkumgebung untersuchen |
| Supportdaten auswerten | häufige Probleme aus Tickets oder Störungen erkennen           |

Welche Methode sinnvoll ist, hängt vom Projekt ab.

Bei kleinen Arbeitsplatzprojekten reicht oft ein Gespräch mit Checkliste.  
Bei größeren Projekten sind Workshops, Dokumentenanalyse und technische Systemprüfung sinnvoller.

---

## Interview und Rückfragen

Ein Interview ist eine häufige Methode, um Anforderungen zu erfassen.

Wichtig ist, nicht nur geschlossene Fragen zu stellen, sondern auch offene Fragen.

### Offene Fragen

Offene Fragen helfen, den Bedarf besser zu verstehen.

Beispiele:

- Welche Aufgaben erledigen Sie täglich mit dem System?
- Welche Probleme treten aktuell auf?
- Was soll sich durch die neue Lösung verbessern?
- Welche Programme werden regelmäßig genutzt?
- Welche Arbeitsabläufe sind besonders wichtig?

### Geschlossene Fragen

Geschlossene Fragen helfen, konkrete Punkte zu klären.

Beispiele:

- Wird ein zweiter Monitor benötigt?
- Wird WLAN oder LAN genutzt?
- Soll das Gerät im Homeoffice verwendet werden?
- Gibt es eine bestimmte Softwareversion?
- Gibt es ein festes Budget?

Gute Anforderungsaufnahme besteht meistens aus beiden Fragearten.

---

## Anforderungen richtig formulieren

Anforderungen sollten klar, verständlich und prüfbar formuliert werden.

Schlechte Formulierungen sind ungenau.

Beispiele für ungenaue Anforderungen:

- Der PC soll schnell sein.
- Das System soll sicher sein.
- Der Arbeitsplatz soll modern sein.
- Der Benutzer soll gut arbeiten können.

Besser sind konkrete und prüfbare Anforderungen:

- Der Arbeitsplatz soll zwei externe Monitore unterstützen.
- Das Gerät soll mindestens 16 GB RAM besitzen.
- Die Festplatte soll mit BitLocker oder einer vergleichbaren Lösung verschlüsselt werden.
- Der Benutzer soll Zugriff auf die Netzlaufwerke der Abteilung erhalten.
- Die Fachsoftware Version X soll installiert und getestet sein.

Eine gute Anforderung kann später überprüft werden.

---

## Eigenschaften guter Anforderungen

Gute Anforderungen sollten bestimmte Eigenschaften haben.

| Eigenschaft      | Bedeutung                              |
| ---------------- | -------------------------------------- |
| eindeutig        | nicht missverständlich                 |
| vollständig      | enthält alle wichtigen Informationen   |
| prüfbar          | kann getestet oder kontrolliert werden |
| realistisch      | technisch und wirtschaftlich umsetzbar |
| nachvollziehbar  | Herkunft und Grund sind bekannt        |
| priorisiert      | Wichtigkeit ist klar                   |
| widerspruchsfrei | passt zu anderen Anforderungen         |

Unklare Anforderungen führen oft zu Nacharbeit, Diskussionen und Fehlentscheidungen.

---

## Funktionale Anforderungen

Funktionale Anforderungen beschreiben, was ein System tun soll.

Beispiele:

- Benutzer können sich anmelden.
- Der Arbeitsplatz kann auf das Firmennetzwerk zugreifen.
- Die Fachsoftware kann gestartet werden.
- Der Benutzer kann auf einen Netzwerkdrucker drucken.
- Dateien können auf einem Netzlaufwerk gespeichert werden.
- Der Laptop kann über eine Dockingstation zwei Monitore nutzen.

Funktionale Anforderungen sind oft direkt sichtbar und testbar.

---

## Nicht-funktionale Anforderungen

Nicht-funktionale Anforderungen beschreiben Eigenschaften oder Qualitätsmerkmale eines Systems.

Sie beschreiben nicht direkt eine einzelne Funktion, sondern die Qualität der Lösung.

Wichtige Bereiche:

| Bereich          | Bedeutung                           |
| ---------------- | ----------------------------------- |
| Leistung         | System arbeitet schnell genug       |
| Verfügbarkeit    | System ist zuverlässig erreichbar   |
| Sicherheit       | Daten und Zugriff sind geschützt    |
| Bedienbarkeit    | Benutzer können gut damit arbeiten  |
| Wartbarkeit      | IT kann System einfach pflegen      |
| Skalierbarkeit   | Lösung kann später erweitert werden |
| Kompatibilität   | passt zu vorhandenen Systemen       |
| Energieeffizienz | verbraucht angemessen wenig Strom   |

Nicht-funktionale Anforderungen sind oft entscheidend für den späteren Betrieb.

---

## Technische Analyse

Bei der technischen Analyse wird geprüft, welche technischen Bedingungen vorhanden sind.

Dazu gehören:

- vorhandene Hardware
- vorhandene Software
- Betriebssysteme
- Netzwerkstruktur
- IP-Adressierung
- WLAN oder LAN-Anbindung
- Serverdienste
- Benutzerverwaltung
- Druckerumgebung
- Speicherorte
- Backup-Lösungen
- Sicherheitssoftware
- Lizenzbestand
- vorhandene Dokumentation

Diese Informationen sind wichtig, damit neue Systeme sauber integriert werden können.

Ein neues Gerät muss nicht nur einzeln funktionieren, sondern in die vorhandene Umgebung passen.

---

## Systemvoraussetzungen prüfen

Bei Software und Hardware müssen Systemvoraussetzungen geprüft werden.

Systemvoraussetzungen beschreiben, welche technischen Mindestbedingungen erfüllt sein müssen.

Beispiele:

| Bereich        | Mögliche Voraussetzung                     |
| -------------- | ------------------------------------------ |
| Betriebssystem | Windows 11 Pro, Linux, macOS               |
| CPU            | bestimmte Architektur oder Mindestleistung |
| RAM            | mindestens 8 GB oder 16 GB                 |
| Speicher       | freie SSD-Kapazität                        |
| Grafik         | bestimmte GPU oder Treiberversion          |
| Netzwerk       | stabile Verbindung oder bestimmte Ports    |
| Rechte         | lokale Adminrechte oder Domänenrechte      |
| Abhängigkeiten | Frameworks, Laufzeitumgebungen, Treiber    |

Mindestanforderungen reichen oft nur für den Start. Für produktives Arbeiten sind empfohlene Anforderungen meistens sinnvoller.

---

## Mindestanforderungen und empfohlene Anforderungen

Viele Hersteller unterscheiden zwischen Mindestanforderungen und empfohlenen Anforderungen.

| Art                      | Bedeutung                              |
| ------------------------ | -------------------------------------- |
| Mindestanforderungen     | Software läuft grundsätzlich           |
| empfohlene Anforderungen | Software läuft sinnvoll und stabil     |
| Praxisanforderungen      | Anforderungen aus echtem Arbeitsalltag |

Mindestanforderungen sollten nicht blind als Planungsgrundlage genutzt werden.

Ein System kann zwar starten, aber im Alltag trotzdem langsam oder unzuverlässig sein.

Für Unternehmensarbeitsplätze sind empfohlene Anforderungen und reale Nutzung wichtiger.

---

## Priorisierung von Anforderungen

Nicht alle Anforderungen sind gleich wichtig.

Eine einfache Einteilung ist:

| Priorität  | Bedeutung                             |
| ---------- | ------------------------------------- |
| Muss       | zwingend erforderlich                 |
| Soll       | wichtig, aber nicht absolut notwendig |
| Kann       | optional                              |
| Nicht-Ziel | bewusst nicht Teil des Projekts       |

Diese Priorisierung hilft bei Entscheidungen, besonders wenn Budget oder Zeit begrenzt sind.

Muss-Anforderungen müssen erfüllt werden.  
Soll-Anforderungen sollten möglichst erfüllt werden.  
Kann-Anforderungen werden nur umgesetzt, wenn es sinnvoll und möglich ist.

---

## Zielkonflikte

Bei Anforderungen gibt es oft Zielkonflikte.

Ein Zielkonflikt entsteht, wenn zwei Anforderungen nicht gleichzeitig optimal erfüllt werden können.

Beispiele:

| Ziel 1           | Ziel 2             | Konflikt                                      |
| ---------------- | ------------------ | --------------------------------------------- |
| niedrige Kosten  | hohe Leistung      | starke Hardware kostet mehr                   |
| hohe Sicherheit  | einfache Bedienung | zusätzliche Anmeldung kann Benutzer stören    |
| mobiles Gerät    | große Leistung     | leistungsstarke Geräte sind oft schwerer      |
| viele Funktionen | einfache Wartung   | komplexe Systeme sind schwieriger zu betreuen |
| Cloud-Nutzung    | Datenschutz        | Datenverarbeitung muss genau geprüft werden   |

Ein FISI muss solche Konflikte erkennen und sinnvoll erklären.

---

## Dokumentation der Analyse

Die Ergebnisse der Analyse müssen dokumentiert werden.

Eine gute Dokumentation enthält:

- Ausgangssituation
- Problem oder Bedarf
- beteiligte Personen
- technische Umgebung
- funktionale Anforderungen
- nicht-funktionale Anforderungen
- Sicherheitsanforderungen
- rechtliche Anforderungen
- Prioritäten
- Annahmen
- offene Fragen
- Risiken
- Akzeptanzkriterien
- geplante nächste Schritte

Dokumentation sorgt dafür, dass Entscheidungen nachvollziehbar bleiben.

---

## Akzeptanzkriterien

Akzeptanzkriterien legen fest, wann eine Lösung als erfolgreich umgesetzt gilt.

Sie sollten klar und testbar sein.

Beispiele:

- Benutzer kann sich erfolgreich anmelden.
- Fachsoftware startet ohne Fehlermeldung.
- Netzwerkdrucker ist erreichbar.
- Zwei Monitore funktionieren über die Dockingstation.
- Festplattenverschlüsselung ist aktiv.
- Updates sind installiert.
- Zugriff auf Netzlaufwerk funktioniert.
- Benutzer hat keine unnötigen Administratorrechte.

Akzeptanzkriterien sind wichtig für Tests, Übergabe und Abnahme.

---

## Risiken in der Analyse

Schon während der Analyse sollten Risiken erkannt werden.

Typische Risiken:

- Anforderungen sind unklar
- Budget reicht nicht aus
- Lieferzeiten sind zu lang
- Software ist nicht kompatibel
- alte Systeme sind schlecht dokumentiert
- Sicherheitsanforderungen werden unterschätzt
- Benutzer akzeptieren neue Lösung nicht
- vorhandene Hardware ist zu schwach
- Lizenzen fehlen oder sind unklar

Risiken sollten früh dokumentiert und besprochen werden.

---

## Ergebnis der Anforderungsanalyse

Am Ende der Anforderungsanalyse sollte klar sein:

- welches Problem gelöst wird
- welche Anforderungen erfüllt werden müssen
- welche Anforderungen optional sind
- welche technischen Voraussetzungen gelten
- welche Systeme betroffen sind
- welche Risiken bestehen
- welche Kriterien für die Abnahme gelten
- welche Lösung grundsätzlich geeignet ist

Dieses Ergebnis ist die Grundlage für Angebot, Pflichtenheft, Beschaffung und Umsetzung.

---

## Praxisbeispiele

### Beispiel 1: Neue Büroarbeitsplätze

Ein Unternehmen möchte neue Arbeitsplätze für die Verwaltung. In der Analyse wird geklärt, welche Programme genutzt werden, ob zwei Monitore benötigt werden, welche Drucker verwendet werden und welche Zugriffe auf Netzlaufwerke notwendig sind.

### Beispiel 2: Softwareeinführung

Eine Fachabteilung möchte eine neue Software einsetzen. Vor der Installation müssen Betriebssystem, Hardwareleistung, Lizenzen, Benutzerrechte, Datenschutz und Schnittstellen zu bestehenden Systemen geprüft werden.

### Beispiel 3: Homeoffice-Ausstattung

Mitarbeiter sollen regelmäßig von zu Hause arbeiten. Die Analyse klärt, welche Geräte benötigt werden, wie der sichere Zugriff erfolgt, welche Daten geschützt werden müssen und wie Support im Fehlerfall funktioniert.

---

## Typische Fehler

| Fehler                                     | Problem                                |
| ------------------------------------------ | -------------------------------------- |
| Anforderungen nicht schriftlich festhalten | Missverständnisse entstehen            |
| nur mit Entscheidern sprechen              | echte Benutzerbedürfnisse fehlen       |
| technische Umgebung nicht prüfen           | Lösung passt nicht zur Infrastruktur   |
| Mindestanforderungen zu niedrig planen     | System ist später langsam              |
| Sicherheit zu spät beachten                | Nachbesserung wird aufwendig           |
| keine Prioritäten setzen                   | Entscheidungen werden schwierig        |
| Risiken ignorieren                         | Probleme treten erst bei Umsetzung auf |
| Akzeptanzkriterien vergessen               | Abnahme wird unklar                    |

---

## FISI-Bezug

Für Fachinformatiker für Systemintegration ist die Bedarfs- und Anforderungsanalyse eine wichtige Grundlage der täglichen Arbeit.

Ein FISI muss technische Informationen erfassen, Kundenbedürfnisse verstehen und daraus konkrete Anforderungen ableiten.

Dabei geht es nicht nur um Hardwaredaten, sondern um das gesamte System: Benutzer, Netzwerk, Sicherheit, Software, Kosten, Wartung und Dokumentation.

Eine gute Analyse sorgt dafür, dass die spätere Lösung technisch passend, wirtschaftlich sinnvoll und zuverlässig betreibbar ist.

---

## Kurze Zusammenfassung

Die Bedarfsanalyse klärt, welches Problem oder welcher Bedarf besteht.

Die Anforderungsanalyse beschreibt, welche konkreten Bedingungen die Lösung erfüllen muss.

Wichtig sind Ist-Zustand, Soll-Zustand, beteiligte Personen, funktionale und nicht-funktionale Anforderungen, technische Voraussetzungen, Prioritäten, Risiken und Akzeptanzkriterien.

Für FISI ist diese Analyse entscheidend, weil sie die Grundlage für Planung, Angebot, Pflichtenheft, Beschaffung, Umsetzung und Übergabe bildet.
